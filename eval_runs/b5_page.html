Systems reliability note 05

When automated deployments fail

Failure rises with batch size, but recovery cost depends more on detection lag and rollback design than on the initiating change.

Mara Voss, Reliability Research18 September 20262,400 word note

Key findings

  1. Small deployments failed less often, while the sharpest increase appeared once a release crossed fifty changed files.
  2. Configuration faults caused fewer events than code faults, yet their slower detection made them the most expensive class per incident.
  3. Rollback readiness cut median recovery time more reliably than adding approval steps before an automated deployment.
  4. Observed associations support smaller batches and better recovery paths, but they do not prove either practice caused lower failure.

Longform text spine

Method: follow the deployment, not the ticket

Unit of analysis: one production deployment. Failure window: start of deployment through the next 24 hours.

Automated deployment is often discussed as a binary capability: a team either has a pipeline or it does not. That framing hides the operational question. Pipelines fail in several ways, at different points, with different consequences. This note treats each production deployment as an exposure and asks whether it produced a service impairment, urgent remediation, or rollback within twenty four hours. The definition follows the practical spirit of change failure rate used in software delivery research, while keeping the event boundary visible enough for audit.1

We assembled deployment records, incident timelines, repository metadata, and change tickets from participating teams for a twelve month observation window. A deployment entered the study when an automated system moved a versioned artifact or configuration set into a customer serving environment. Manual database maintenance, planned resilience tests, and releases to internal sandboxes were excluded. Retries of the same release counted once unless a later retry introduced a new artifact. This avoids inflating failure counts when a controller makes several attempts to converge on one desired state.

A failure required evidence in at least two records. Examples include a monitoring alert paired with a rollback, a customer impact note paired with an emergency patch, or an incident declaration paired with a deployment identifier. A red pipeline stage alone did not qualify if production remained unchanged. Likewise, an error discovered in production counted even when a progressive delivery controller contained it before most customers saw it. This distinction matters because automation can reduce impact without preventing the initiating defect.

Deploy size was estimated from changed files in the source revision set because that field was available across all participating systems. It is an imperfect proxy. A one line policy edit may carry more risk than hundreds of generated files. We therefore used broad bands and checked the pattern against changed line count and number of touched components. The direction remained stable, although exact rates moved. The analysis is descriptive. It reports observed frequencies and costs, then tests whether alternative groupings erase the main pattern.

Two reviewers coded every qualifying event into one primary failure class. Disagreements were resolved against the earliest action that could have prevented customer impact, rather than the final symptom. That rule assigns a malformed feature flag to configuration even if it later exhausts application threads. It assigns an incompatible schema assumption to dependency or data even if application code emitted the first visible error. The taxonomy is intentionally small so engineering leaders can use it without a specialist incident database.

Sample: diverse systems, shared selection pressure

The sample favors teams with enough instrumentation to reconstruct events. That improves measurement and limits generalization.

The final sample contains 38,214 production deployments across 342 services operated by 61 teams. Participants ranged from consumer software groups with frequent edge releases to business systems teams deploying several times each week. Most services ran on managed container platforms. A smaller group used serverless runtimes or virtual machines. No team was selected at random. Participation depended on usable logs, stable identifiers, and willingness to share deidentified operational records.

That selection pressure is visible in the composition. These teams automate more of the path to production than the wider software industry. They also keep richer records when a release goes wrong. The observed overall failure rate should not be read as an industry benchmark. Its value is comparative: the same inclusion rules can be applied across deployment sizes, failure classes, and recovery conditions inside the sample.

Team size and deployment frequency varied together, so a simple comparison could mistake organizational scale for release risk. We calculated rates within each team first, then combined those estimates with deployment weighted summaries. We also reviewed the pattern separately for high frequency and lower frequency teams. Large batches failed more often in both groups. The gap was narrower among teams with automated rollback, strong health checks, and rehearsed incident ownership.

The study recorded 4,729 qualifying failures. Most were contained without a public incident, which explains why incident registers alone understate deployment problems. Conversely, raw pipeline error counts overstate customer risk because many errors occur before production changes. The linked record method sits between those extremes. It captures production remediation while refusing to label every failed automation step as a deployment failure.

Three failure classes, three control points

Classes name earliest useful control point: code behavior, configuration state, or dependency and data compatibility.

Code behavior failures were the most common class. They included exceptions on newly exercised paths, incorrect business logic, resource leaks, and performance regressions introduced by an application revision. These events were usually detected quickly because the changed process emitted familiar signals. Tests and staged rollout reduced exposure, but neither removed it. The useful control was often a narrow canary with explicit abort criteria, followed by a rollback that did not require rebuilding the artifact.

Configuration failures were less frequent and more elusive. Invalid limits, permission changes, routing rules, feature flags, and environment differences often produced partial symptoms rather than a clean crash. A service could remain healthy under platform checks while serving the wrong behavior to one region or customer segment. Detection therefore depended on product and policy signals, not only infrastructure telemetry. Teams paid for this gap in investigation time. The initiating edit was small, yet the search space crossed deployment systems, secret stores, policy engines, and application owners.

Dependency and data failures joined compatibility mistakes that became visible only when a new version met an external service, schema, queue, cache, or persistent record. They were not always caused by the deployed component. A release could expose an old invariant that previous traffic never exercised. Forward compatible schema changes, contract tests, and explicit dependency budgets reduced these events. Recovery was difficult when the deployment had already written data that an older version could not read.

The size curve is monotonic, but size does not act alone. Bigger deployments touched more components, waited longer in queues, and more often combined application, configuration, and schema changes. Each trait can raise risk. The chart should therefore be read as a planning signal, not a natural law. Dividing work into smaller independently deployable units may help, provided the split does not create hidden coordination or force users through incompatible intermediate states.

Across classes, reliable recovery had three properties. Detection used a signal tied to customer behavior. The prior version remained deployable without manual reconstruction. Ownership was assigned before the release, including authority to stop rollout. Teams sometimes substituted approval layers for these capabilities. Approvals caught known hazards but did little for novel interactions after production traffic arrived. The most resilient systems treated release as a reversible experiment, an approach consistent with continuous delivery practice and research on high performing technology organizations.23

Cost model: time, interruption, and delayed learning

Cost is engineering labor valued at a common loaded rate. Revenue loss and customer compensation are excluded.

A failure rate alone cannot rank improvement work. A frequent fault that rolls back automatically in four minutes may consume less engineering capacity than a rare configuration error that remains ambiguous for two hours. We estimated direct cost from active response time, number of responders, follow up repair time, and interruption overhead. To compare organizations without disclosing pay data, labor was valued at a common loaded rate of 140 dollars per engineer hour. This is a modeling choice, not a claim about compensation.

Interruption overhead adds fifteen minutes for each responder pulled from planned work. The allowance represents context recovery after an urgent page, not time spent in the incident itself. Follow up includes the durable repair and tests directly linked to the failure, but excludes broad platform projects proposed during review. Customer loss, contractual penalties, and reputational effects are omitted because participants measured them inconsistently. As a result, the table is a lower bound on business cost and a more useful view of engineering demand.

Configuration produced the highest median direct cost despite representing fewer events. Detection lag was the main difference. Responders spent time establishing whether the application, platform, identity layer, or rollout controller owned the symptom. This suggests a practical priority: make effective configuration visible beside the running version, record who changed it, and test customer level behavior after rollout. Faster rollback helps only when teams know what state to restore.

Dependency and data failures had the longest recovery. Once a release changed durable state, reverting code could deepen incompatibility. The safer response often required a forward repair, migration pause, or compatibility bridge. Investments in expand and contract schema changes, replayable writes, and consumer driven contract tests target this cost. They may add work before release, but the cost model asks whether that work replaces more expensive emergency coordination rather than whether it makes every individual deployment faster.

We tested the model with labor rates from 90 to 220 dollars per hour and interruption allowances from zero to thirty minutes. The class ordering did not change. Absolute amounts did. This stability supports prioritizing detection for configuration and reversibility for data changes. It does not justify a universal return estimate. Each organization should replace the common labor rate, include its own customer impact, and separate time that would have been spent on the repair even without an incident.

Limitations: useful pattern, bounded claim

Strongest claim: these variables travel together in this instrumented sample. Causality remains unproven.

This study is observational. Teams choose batch size, architecture, controls, and deployment frequency together. A team that ships small changes may also have clearer ownership, better tests, and a simpler system. Statistical adjustment cannot remove unmeasured differences. The association between deploy size and failure should not be interpreted as proof that splitting any given change will reduce risk by the amount shown in the chart.

The sample is also selective. Participating teams had stable deployment identifiers and incident evidence rich enough to link records. Less instrumented organizations may experience different rates and much larger detection gaps. Container platforms dominate the sample, while mobile clients, embedded software, safety critical systems, and long lived enterprise releases are absent. Practices suited to these services may transfer poorly where rollback is impossible or releases require coordinated physical action.

Measurement choices shape results. Changed files is a crude size proxy. The twenty four hour window misses latent faults and may include unrelated failures. Two record confirmation reduces false positives but misses quiet customer harm. Primary class coding compresses incidents with several contributing causes. Cost estimates omit revenue, trust, and opportunity cost, while the common labor rate obscures regional and role differences. Median values hide a long tail of rare, severe events.

Automation maturity changed during the observation period. Several teams added progressive delivery, policy checks, or new telemetry. The analysis treats their records as one sample rather than a controlled before and after experiment. Shared vendors and platform services also create dependence between events, so the effective sample is smaller than the deployment count suggests. Confidence in exact percentages should therefore be lower than the large denominator implies.

Even with those limits, three decisions are supported. Measure production remediation, not pipeline redness. Review release size as a risk signal without turning it into a quota. Fund detection and reversible state transitions alongside prevention. These choices align with established continuous delivery guidance, the emphasis on small batches in delivery research, and systems safety work that treats accidents as interactions rather than single component defects.456

The conclusion is narrower than a slogan: within this sample, larger deployments failed more often, while slow detection and irreversible state made failures expensive. Leaders should use that pattern to ask better local questions. Which releases cannot be reversed? Which signals reveal wrong customer behavior? Which configuration changes lack an owner? The answers matter more than copying a benchmark, because deployment safety is produced by the whole operating system around a change. Local measurement should preserve these distinctions, publish uncertainty, and track recovery outcomes before teams turn a comparative signal into a target.
